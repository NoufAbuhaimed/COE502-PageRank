## 3. The five topics and the evidence for each

**Load imbalance (uniform vs skewed).** In the pull loop, node v costs about in-degree(v) work.
`static` gives each thread the same number of *nodes*; on a skewed graph a few nodes hold most of
the edges, so one thread gets far more *edges* than the others and the rest wait at the barrier.

- Evidence: `datasets` (top-1% share), `imbalance` (max/mean for static on `pr_s500k_5m` vs
  `pr_u500k_5m`), `thread_imbalance.png`.

**Scheduling overhead.** `dynamic,c` fixes the balance by handing out chunks of c nodes from a
shared counter, but every chunk is one atomic operation on a shared cache line. Small chunks
balance better and cost more; large chunks cost less and balance worse. `edge-balanced` splits by
edge count once, before timing, so it balances with no per-iteration cost.

- Evidence: `sweep` (best chunk, and where small chunks get slower), `chunk_sweep.png`.

**Synchronization at iteration boundaries.** Iteration t+1 can't start until every rank of
iteration t is written, so each iteration ends with a barrier: two in `parallel.cpp` (one per
`omp for`), one plus a `single` in `parallel_opt.cpp`. A barrier costs more as P grows, and the
whole team waits for the slowest thread.

- Evidence: small graphs (little work per barrier) scale worst in Q1, and e rises with P in Q2.

**Reduction overhead.** `dangling` (sum) and `max_change` (max) are combined across threads every
iteration. `parallel_opt.cpp` combines per-thread values padded to one cache line each
(`PaddedDouble`, `src/thread_times.hpp`) to avoid false sharing.

- Evidence: compare static/dynamic with edge-balanced on the uniform graphs, where balance is
  already good, so the gap is mostly region, barrier and reduction cost.

**Memory bandwidth and caches.** Each edge costs one 4-byte index read plus one random 8-byte read
of `c[in[k]]`, with almost no arithmetic. That makes PageRank memory-bound: once enough threads
saturate the memory bandwidth, more threads add nothing. The small graphs fit in cache (see
"Data touched / iter" next to the L3 size), the large ones don't.

- Evidence: `bandwidth` (does GB/s stop growing at some P?), `system` (L3 size, memory).
- **Logical vs physical cores.** On cloud VMs a vCPU is usually one hyperthread, so
  16 vCPUs = 8 physical cores. Two threads on one core share its caches and memory port; look
  for a change in slope between P = 8 and P = 16.
