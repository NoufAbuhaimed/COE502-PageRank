# Q2 — Effective serial fraction

The Karp–Flatt metric turns every measured speedup into an "effective serial fraction" e. How e
changes with the thread count separates two causes of lost speedup: work the algorithm can't
parallelize, and overhead that parallelism adds. Needs the benchmark results from
[Q1](Q1.md) (steps 1–7).

PDF section covered: *Performance analysis*, "Distinguish algorithmic serial work from parallel
overheads that make the effective serial fraction increase as P grows."

---

## 1. The formula

For P threads with measured speedup S (S = T1 / Tp, T1 = the serial program):

```
e = (1/S − 1/P) / (1 − 1/P)        (defined for P > 1)
```

It is Amdahl's law solved for the serial fraction. If the program really had a fixed serial part f
and no other losses, e would equal f at every P.

| What e does as P grows | What it means |
| --- | --- |
| Stays about the same | Lost speedup comes from fixed serial work (Amdahl). |
| Rises | Lost speedup comes from overhead that grows with P: barriers, reductions, scheduling, memory-bandwidth contention, thread start-up. |
| Near 0 | Close to ideal speedup. |
| Negative | Superlinear speedup, usually because each thread's share now fits in cache. |

## 3. Where the serial work and the overheads are in the code

Use this map to explain *why* e behaves the way it does.

**Serial work inside the timed loop** (`src/parallel.cpp`): small, O(1) per iteration.

| What | Where |
| --- | --- |
| `base = (1-d)/N + d·dangling/N` | `src/parallel.cpp:77` |
| Swap the two rank buffers, count the iteration | `src/parallel.cpp:111` |
| Convergence test `max_change < tol` | `src/parallel.cpp:113` |

Not in the timed region (excluded on purpose): reading the file and building the CSR
(`src/graph.cpp`), the edge-balanced split (`src/parallel_opt.cpp:61`).

**Parallel overhead that grows with P**:

| Overhead | Where | Per iteration |
| --- | --- | --- |
| Fork/join of a parallel region | `src/parallel.cpp:68` and `:99` | 2 regions |
| Implicit barrier at the end of each `omp for` | same two loops | 2 barriers |
| `reduction(+: dangling)` | `src/parallel.cpp:68` | 1 |
| `reduction(max: mc)` | `src/parallel.cpp:99` | 1 |
| Shared chunk counter for `dynamic` | `schedule(runtime)` with `OMP_SCHEDULE=dynamic,c` | N / c chunk grabs |
| Waiting for the slowest thread (load imbalance) | phase 2 on skewed graphs | — |

`src/parallel_opt.cpp` removes some of these: one parallel region for the whole run, one explicit
barrier plus one `single` per iteration (`src/parallel_opt.cpp:116–130`), no chunk counter. That's
why comparing its e with the other two versions isolates the overhead part.
